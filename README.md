# Well Model Builder

Версия с формулами базы знаний, на основе этапа 08 хакатона «Разработка системы модели скважины». Дашборд строит IPR и VLP и показывает рабочую точку. Автотесты проверяют расчётные сервисы по отдельности и весь путь от параметров скважины до ответа backend.

Для запуска сайта через Nginx см. [Запуск в Docker](#запуск-в-docker-через-nginx). Если на сервере нет Docker/Podman, используйте [нативный запуск через Python venv](#запуск-без-docker-и-podman-через-python-venv).

## Проверка точности

Из корня распакованного проекта выполните в PowerShell с Python 3.11 или новее:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m scripts.verify_accuracy
```

Если окружение проекта уже готово, достаточно последней команды. Для Linux или macOS используйте `python3` и `.venv/bin/python` (Python 3.11 или новее). Команда запускает unittest, поднимает отдельные процессы IPR, VLP, Nodal и backend на свободных локальных портах, ждёт health, отправляет реальные HTTP-запросы, записывает [таблицу проверки](accuracy-report.md) и останавливает процессы. Можно оставить дашборд открытым. Код завершения 0 означает, что все запрошенные проверки пройдены. Код 1 и строки FAIL указывают на ошибку.

На Python 3.12.14 прошли 58 автотестов. Отчёт содержит 129 успешных строк с учётом аналитических и HTTP-проверок. В том числе по архиву well_01 сверены 88 чисел. [Сравнение исходной и обновлённой моделей](docs/well_01_comparison.md).

**Откуда взялся численный контроль.** В водяном примере пластовое давление 30 атм, PI = 0,1 м³/(сут·атм), устьевое давление 10 атм. Вертикальная глубина 110 м, длины участков 100 и 50 м, диаметры 0,062 и 0,100 м. При дебитах 0–4 м³/сут течение ламинарное. Независимые формулы в проверке задают IPR как `p = 30 − 10q` и VLP как `p = p₀ + kq`, где `p₀ = 10 + ρg·110/101325`, а `k = 128μ·(100/0,062⁴ + 50/0,100⁴)/(π·86400·101325)`. Здесь ρ = 1000 кг/м³ и μ = 0,001 Па·с. Решение двух уравнений даёт эталон E2E. Для каждого ненулевого значения сравнивается `100 × |факт − эталон| / |эталон|`. Предел включён, 5 % для каждого сервиса и 10 % для обеих координат E2E. Для нулевого эталона принято точное совпадение с нулём, в таблице показано абсолютное отклонение в единицах координаты.

### Эталоны well_01

Команда проверки выше автоматически использует оригинальные запросы и ответы в `test_data/well_01`. Для другого набора можно указать `--references путь/к/manifest.json --report другой-отчёт.md`. ### Как рассчитывается подъём

- Разбиваем ствол по станциям инклинометрии, башмаку НКТ и точке пласта. Линейная интерполяция TVD по MD даёт вертикальный уклон каждого участка. Если первая станция глубже устья, добавляем начало в (0, 0). При `h_mes=0` весь ствол проходит по эксплуатационной колонне.
- Принят постоянный геотермический градиент по вертикали. Местная температура равна `t_res − geo_grad × (TVD(h_res) − TVD(MD)) / 100`. Для скважины из примера это 57 °C на устье, 87 °C у башмака и 90 °C у пласта.
- Давление интегрируется от заданного `p_wh` вниз методом RK45 с отдельным шагом запуска на каждой границе участков. Градиент в Па/м равен `ρg × dTVD/dMD + f × ρv²/(2d)`. При подъёме потока обе составляющие увеличивают требуемое давление на забое. На горизонтальном участке гидростатическая составляющая равна нулю. Скорость определяется по локальному рабочему объёму всех фаз, при нулевом расходе остаётся гидростатика однородной равновесной смеси.
- Для Re ≤ 2000 применяется ламинарная формула, для Re ≥ 4000 итерационно решается уравнение Colebrook–White для коэффициента Дарси. Переход между граничными значениями линейный. `roughness` подаётся сразу как отношение абсолютной шероховатости к диаметру. [Уравнения Дарси–Вейсбаха и Colebrook–White](https://www.aiche.org/sites/default/files/cep/20161238_r.pdf)

## Расчёт IPR

После запуска всего проекта в Docker откройте [Swagger IPR](http://localhost/ipr/docs). Выберите `POST /ipr/calc`, нажмите **Try it out** и **Execute**. В форму уже подставлен пример из §5.2 ТЗ.

| Поле | Смысл и единицы | Допустимые значения |
| --- | --- | --- |
| `p_res` | Пластовое давление, атм | Больше 0 |
| `wct` | Обводнённость жидкости, % | От 0 до 100 включительно |
| `pi` | Коэффициент продуктивности, м³/(сут·атм) | 0 и выше |
| `pb` | Давление насыщения, атм | 0 и выше |
| `points` | Число точек | Целое от 2 до 201, по умолчанию 21 |

Первые четыре поля обязательны. При ошибке ввода сервис возвращает HTTP 422 и JSON с полем `detail`. В ответе на корректный запрос элементы `p_wf[i]` и `q_liq[i]` образуют одну точку. Давления расположены с равным шагом от 1 атм до `p_res`, оба конца включены. При `p_wf = p_res` дебит равен нулю.

**Контрольный запрос для PowerShell**

```powershell
$body = '{"p_res":200,"wct":100,"pi":1,"pb":150,"points":2}'
Invoke-RestMethod -Method Post -Uri 'http://localhost/ipr/calc' -ContentType 'application/json' -Body $body | ConvertTo-Json -Compress
```

```json
{"q_liq":[199.0,0.0],"p_wf":[1.0,200.0]}
```

Для примера из ТЗ задайте `wct=50` и опустите `points`. При 1 и 10,95 атм первые дебиты, округлённые до сотых, равны 139,98 и 137,93 м³/сут. API отдаёт числа с полной точностью расчёта.

### Формула и граничные случаи

Обозначим `J = pi`, `f = wct / 100`, `B = min(pb, p_res)`. Для насыщенного пласта (`pb >= p_res`) форма Вогеля нормируется на пластовое давление. При нулевой продуктивности весь ряд дебитов равен нулю.

1. При 100% воды или при `p_wf >= B` приток равен `J · (p_res − p_wf)` в области добычи. При `pb = 0` это вся кривая.
2. Для чистой нефти ниже `B` положим `q_b = J · (p_res − B)` и `x = p_wf / B`. Тогда `q_oil = q_b + (J · B / 1.8) · (1 − 0.2x − 0.8x²)`. При `p_wf = B` обе ветви дают `q_b`.
3. Для смеси при одном дебите `q` рассчитываются давление воды `p_water = p_res − q/J` и давление нефти `p_oil` по обращённой кривой Вогеля. Brown задаёт `p_wf(q) = f · p_water + (1 − f) · p_oil`. Код решает это уравнение относительно дебита для каждого давления сетки.
4. При `q_o,max = q_b + J · B / 1.8` нефтяное давление достигает нуля, а давление смеси равно `(4/9) · f · B`. Ниже этого давления используется линейное продолжение по секущей композитной кривой через `0.999 · q_o,max` и `q_o,max`.

ТЗ допускает `0 < p_res < 1` и фиксирует начало сетки в 1 атм. Для этого случая сервис сохраняет оба конца убывающей сетки и возвращает нулевой приток во всех точках, где забойное давление достигает или превышает пластовое. При `p_res = 1` все точки имеют давление 1 атм.

Методика — K. E. Brown, *The Technology of Artificial Lift Methods*, т. 4, PennWell, 1984, с. 30–35. Формулы композитной кривой и секущей приведены у A. C. Kahya, *Analyzing the Design of Submersible Lifted Deviated Oil Wells*, METU, 2005, уравнения 3.10–3.26. Расчёт реализован в проекте и выполняется локально. [Библиографическая ссылка на Brown](https://www.ihsenergy.ca/support/documentation_ca/Harmony_Enterprise/2023_2/content/html_files/ref_materials/analysis_method_theory/oil_ipr_theory.htm) · [Уравнения в работе Kahya](https://open.metu.edu.tr/bitstream/handle/11511/14802/index.pdf)

## Контракт дашборда и backend

Дашборд использует `POST /api/calculate` с `Content-Type: application/json`. Дашборд передаёт данные скважины одним запросом. Обводнённость задаётся один раз в `pvt.wct` и используется обеими моделями. Имена входов и выходов расчётных сервисов соответствуют §5 ТЗ.

### Пример запроса

Тот же JSON сохранён в [examples/calculate.json](examples/calculate.json).

```json
{
  "reservoir": {"p_res": 200, "pi": 1, "pb": 150},
  "well": {
    "inclinometry": {"MD": [0, 1000, 1500], "TVD": [0, 1000, 1100]},
    "casing": {"d": 0.1},
    "tubing": {"d": 0.062, "h_mes": 1000},
    "p_wh": 10, "geo_grad": 3, "h_res": 1500, "roughness": 0.0001
  },
  "pvt": {"wct": 100, "rp": 100, "gamma_oil": 0.8, "gamma_gas": 0.7, "gamma_wat": 1.0, "t_res": 90},
  "sampling": {"ipr_points": 2, "vlp_points": 2, "q_max": 200}
}
```

| Блок | Поля и единицы |
| --- | --- |
| `reservoir` | `p_res` и `pb` в атм, `pi` в м³/(сут·атм). `pb` передаётся в IPR. |
| `well` | `MD`, `TVD`, диаметры `d`, `h_mes`, `h_res` в м, `p_wh` в атм. Относительная шероховатость `roughness` по умолчанию равна 0.0001. Для `geo_grad` команда принимает °C/100 м. |
| `pvt` | `wct` в %, `rp` в м³/т, `gamma_oil`, `gamma_gas`, `gamma_wat` — относительные плотности, `t_res` в °C. |
| `sampling` | Весь блок можно опустить. По умолчанию по 21 точке IPR и VLP и `q_max = 400` м³/сут. Каждая сетка допускает от 2 до 201 точки. |

Числа передаются как конечные JSON-числа. Backend проверяет типы, диапазоны и согласованность геометрии. Имена полей MD и TVD чувствительны к регистру.

### Формат успешного ответа

Для запроса из примера backend возвращает HTTP 200. Значения ниже округлены до пяти знаков.

```json
{
  "ipr": {"q_liq": [199, 0], "p_wf": [1, 200]},
  "vlp": {"q_liq": [0, 200], "p_wf": [116.46252, 117.51846]},
  "operating_point": {"q_liq": 83.09874, "p_wf": 116.90126}
}
```

Пара элементов `q_liq[i]` (м³/сут) и `p_wf[i]` (атм) задаёт узел кривой. Backend отправляет Nodal исходные узлы с полной точностью. Единственный элемент ответа Nodal становится объектом `operating_point`.

### Контрольные сценарии

Каждая строка задаёт отдельное изменение исходного файла `examples/calculate.json`.

| Изменение | HTTP | Что проверить |
| --- | --- | --- |
| Установить `pvt.wct = 50` и удалить блок `sampling` | 200 | По 21 точке в обеих кривых. Рабочая точка около 127,99036 м³/сут и 49,70857 атм. |
| Установить `pvt.wct = 101` | 422 | Backend указывает путь `body.pvt.wct`. |
| Установить `well.p_wh = 210` | 422 | `NODAL — Кривые IPR и VLP не пересекаются.` |
| Отправить исходный запрос при недоступном VLP | 503 | `VLP — сервис недоступен.` |

Ошибки возвращаются как JSON с полем `detail`. При превышении времени ожидания backend возвращает HTTP 504, при повреждённом или неожиданном ответе сервиса — HTTP 502. В обоих случаях указан этап.

## Запуск без Docker и Podman через Python venv

Этот вариант запускает все компоненты непосредственно на хосте: три расчётных API, backend и веб-интерфейс. Docker, Podman, Nginx и база данных для проекта не требуются. Нужен **Python 3.11 или новее** и доступ к PyPI на время установки пакетов. Зависимости приложения закреплены в lock-файле; этот диапазон поддерживают используемые версии NumPy и SciPy.

Сначала распакуйте архив и перейдите в каталог `Well` — туда, где находятся `requirements.lock` и `scripts/`. Все команды ниже нужно выполнять из этого каталога.

### Windows (PowerShell)

Убедитесь, что Python 3.11 или новее доступен через Python Launcher:

```powershell
py -3 --version
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
```

Для запуска тестов дополнительно установите зависимости разработки:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.lock
.\.venv\Scripts\python.exe -m pytest -q
```

### Linux и macOS (Bash/Zsh)

Убедитесь, что `python3 --version` показывает Python 3.11 или новее. Debian 12 со штатным Python 3.11 подходит. На минимальных Linux-образах модуль `venv` может устанавливаться отдельно. В Debian/Ubuntu выполните `sudo apt update && sudo apt install python3-venv`, если `python3 -m venv` сообщает об отсутствии модуля.

```bash
python3 --version
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.lock
```

Для тестов:

```bash
.venv/bin/python -m pip install -r requirements-dev.lock
.venv/bin/python -m pytest -q
```

Команды установки одинаковы для Linux и macOS. Виртуальное окружение не нужно активировать: вызов Python по пути внутри `.venv` исключает зависимость от оболочки и политики активации PowerShell. При желании окружение можно активировать обычным способом: `.\.venv\Scripts\Activate.ps1` в PowerShell или `source .venv/bin/activate` в Bash/Zsh.

### Запуск и проверка

Запустите полный проект из корня распакованной папки. Окно терминала должно оставаться открытым:

**Windows:**

```powershell
.\.venv\Scripts\python.exe scripts/run_local.py
```

**Linux/macOS:**

```bash
.venv/bin/python scripts/run_local.py
```

Откройте `http://127.0.0.1:3000/` — это главная страница. Страница состояния находится по адресу `http://127.0.0.1:3000/services.html`, Swagger backend — `http://127.0.0.1:8080/docs`.

Для проверки из второго окна терминала запустите:

**Windows:**

```powershell
.\.venv\Scripts\python.exe scripts/smoke.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -q
```

**Linux/macOS:**

```bash
.venv/bin/python scripts/smoke.py
.venv/bin/python -m unittest discover -s tests -q
```

Успешная команда `smoke.py` проверяет доступность frontend, health всех API, Swagger/OpenAPI и совпадение общего расчёта с прямыми вызовами IPR, VLP и Nodal. Для запуска только расчётных сервисов добавьте `--core` одновременно к `scripts/run_local.py` и `scripts/smoke.py --core`. Остановить запущенные сервисы можно сочетанием `Ctrl+C` в первом окне. При нативном запуске Swagger UI получает JS/CSS с CDN `jsdelivr.net`; если CDN недоступен, интерактивная страница `/docs` может не отобразиться, но API и `/openapi.json` продолжат работать. В Docker-образе Swagger UI поставляется локально.

### Запуск на удалённом сервере

По умолчанию сервисы слушают только `127.0.0.1`, поэтому доступны лишь с самого сервера. Чтобы открыть веб-интерфейс по IP или имени сервера, укажите `--host 0.0.0.0` и добавьте origin страницы в CORS. Например, для сервера с адресом `192.0.2.10`:

**Linux/macOS:**

```bash
.venv/bin/python scripts/run_local.py --host 0.0.0.0 --frontend-origin http://192.0.2.10:3000
```

**Windows:**

```powershell
.\.venv\Scripts\python.exe scripts/run_local.py --host 0.0.0.0 --frontend-origin http://192.0.2.10:3000
```

Замените `192.0.2.10` на IP или доменное имя сервера. Для другого origin можно повторить `--frontend-origin`, например при нескольких доменах. После запуска откройте `http://192.0.2.10:3000/`.

В нативном режиме браузер обращается к компонентам напрямую, поэтому с клиентской машины должны быть доступны TCP-порты **3000, 8002, 8003, 8004 и 8080**. Ограничьте доступ к ним правилами firewall только доверенными адресами. `0.0.0.0` открывает все эти сервисы на сетевых интерфейсах сервера. Не публикуйте их напрямую в открытый Интернет: нативный режим работает по HTTP; для публичного доступа используйте Docker-вариант с Nginx или отдельно настройте reverse proxy с TLS и маршрутами ко всем пяти портам. Для локального доступа оставляйте значение `127.0.0.1` по умолчанию.

При необходимости изменить порт backend используйте `--backend-port 18080`. Frontend автоматически получит этот порт через `backend-port.js`; при этом порт 3000 и порты расчётных API остаются прежними. Для постоянной работы на Linux используйте менеджер служб, например systemd. Создайте `/etc/systemd/system/well-model-builder.service` и замените имя пользователя и путь к проекту на свои:

```ini
[Unit]
Description=Well Model Builder
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=YOUR_LINUX_USER
WorkingDirectory=/opt/Well
ExecStart=/opt/Well/.venv/bin/python /opt/Well/scripts/run_local.py --host 127.0.0.1
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Затем включите службу:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now well-model-builder
sudo systemctl status well-model-builder
```

Логи смотрите командой `journalctl -u well-model-builder -f`. Для доступа по сети добавьте к `ExecStart` параметры `--host 0.0.0.0 --frontend-origin http://SERVER_IP:3000` и настройте firewall согласно предупреждению выше.

| `shared/contracts.py`, `shared/api.py` | Схемы JSON и правила HTTP. |
