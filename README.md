# Well Model Builder

Версия с формулами базы знаний, на основе этапа 08 хакатона «Разработка системы модели скважины». Дашборд строит IPR и VLP и показывает рабочую точку. Автотесты проверяют расчётные сервисы по отдельности и весь путь от параметров скважины до ответа backend.

Для запуска без контейнеров используйте раздел [Нативный запуск через Python + venv](#нативный-запуск-без-dockerpodman-python--venv). Для контейнерного запуска через Nginx см. [Запуск в Docker](#запуск-в-docker-через-nginx).

## Well AI на сайте (Windows и Docker Desktop)

1. Запустите Ollama. Команда `ollama list` покажет доступные модели. Шаблон настроен на `qwen3:8b`. При первом запуске загрузите её командой `ollama pull qwen3:8b`.
2. В новой папке с `compose.yaml` выполните в PowerShell:

```powershell
Copy-Item .env.example .env
docker compose up -d --build
```

Если у вас уже есть рабочий файл настроек Ollama из предыдущей версии, можно использовать его. Откройте http://localhost/ и нажмите «Рассчитать по форме» в панели Well AI. Ассистент использует IPR, VLP и Nodal, показывает рабочую точку и график. Для проверки отдельного диалога отправьте текст из `examples/assistant_text.txt` или JSON из `examples/calculate.json`.

Кнопка «Проверить» читает конфигурацию backend. Реальный вызов модели выполняется при отправке сообщения. Если чат сообщил об ошибке подключения, проверьте из контейнера, видит ли он Ollama и установленную модель:

```powershell
docker compose exec backend python -c "import httpx; print(httpx.get('http://host.docker.internal:11434/api/tags').json())"
```

Адрес для Docker Desktop задаётся в `LLM_BASE_URL`, имя установленной модели — в `LLM_MODEL`. Для удалённого OpenAI-совместимого провайдера укажите также ключ в `LLM_API_KEY`. После изменения настроек выполните `docker compose up -d backend`. При нативном запуске задайте переменные в PowerShell перед запуском `scripts/run_local.py`, для локальной Ollama используйте `http://127.0.0.1:11434/v1`.

Чат принимает данные в несколько сообщений и уточняет пропуски. Кнопка согласования применяет предложенные значения по умолчанию. При ручном редактировании выберите, использовать ли исправленную форму или продолжить с данными чата. Подсказки под полями показывают связанные параметры и конкретные ячейки MD/TVD. Серверный контекст хранится в памяти backend в пределах сессии; видимая история сохраняется в браузере.

## Этап 3 — естественный диалог и синхронизация

Чат различает обычный вопрос (`mode: conversation`), ввод без запуска (`parameters`) и запрос расчёта (`calculation`). Приветствие, теоретический вопрос или обсуждение результата не запускают вычисления, не запрашивают пропущенные поля и не изменяют форму или график. Для обычного ответа адаптер вызывает LLM без инструментов; сервер дополнительно блокирует попытки расчёта вне разрешённого режима. Пропущенные данные продолжают храниться при отвлечении на вопрос, затем можно вернуться к уточнению. Числовые координаты последнего расчёта вставляются сервером по маркерам `[q_liq]`, `[p_wf]`; значения полей — по `[field:путь]`. Свободные числовые утверждения модели блокируются. С этапа 5 теоретические вопросы получают контекст локальной базы знаний; см. раздел «Этап 5».

После ручного изменения формы чат остаётся доступен для вопросов. Чтобы сменить расчётный набор, нужно выбрать «Рассчитать по форме» или «Продолжить по данным чата». Старый результат относится к сохранённым данным диалога, а не к новой форме. Чат показывает реальные завершённые этапы IPR, VLP, Nodal и их длительность после ответа; это не потоковая индикация прогресса. Ручные проверки полей и подсказки сохранены.

Контроль: отправьте «Привет», «Что такое IPR?», затем JSON из `examples/calculate.json`; уточните «Какой получился дебит?» и убедитесь, что график сохранился. Для неполного JSON удалите `p_res`, задайте теоретический вопрос, затем уточните `Пластовое давление 200 атм`. Проверьте ошибку обводнённости и несогласованных диаметров. Вне темы скважин модель должна вежливо перенаправлять диалог согласно §6.7 ТЗ.

Проверка: `python -m pytest -q`, `node --experimental-default-type=module scripts/check_assistant_ui_logic.mjs`, опционально `python -m scripts.check_assistant_ui` (Playwright/Chromium). Автотесты используют тестовый адаптер LLM; фактическое качество ответов настроенной Ollama необходимо проверить на машине команды. Распознавание намерений и параметров пока опирается на серверные правила и поддерживаемые формы текста; сложные смешанные запросы могут требовать переформулировки. В этой среде браузерный прогон не завершён: Chromium блокирует локальную навигацию политикой администратора.

## CI: автоматическая проверка GitHub Actions

Workflow находится в `.github/workflows/ci.yml`. GitHub Actions запускает его автоматически при каждом `push` и `pull_request`; его также можно запустить вручную через **Actions → Well Model Builder CI → Run workflow**. Для CI не нужны SSH-ключи, LLM API keys, Ollama или другие секреты: тесты используют тестовые адаптеры и локальные расчётные сервисы.

Проверка состоит из двух последовательных jobs:

1. **Python tests, accuracy and frontend logic** — устанавливает Python 3.12 из `requirements-dev.lock`, проверяет зависимости (`pip check`), компилирует Python-модули, запускает весь набор `pytest`, затем `scripts.verify_accuracy` (аналитические эталоны, реальные HTTP-запросы, Nodal и E2E, включая `well_01`) и JavaScript regression checks для Well AI и экспорта отчётов.
2. **Docker build and HTTP integration** — после успешной первой job проверяет Compose-конфигурацию, собирает все Docker-образы, собирает и запускает отдельный Docker target `tests`, поднимает приложение целиком и запускает `scripts/smoke.py --compose` через Nginx. В конце контейнеры останавливаются даже при ошибке проверки.

JUnit-отчёт pytest и `accuracy-report.md` прикладываются к запуску workflow как artifact `test-reports` (хранятся 14 дней). Ошибка на любом обязательном этапе делает CI красным и блокирует успешное завершение workflow.

### Запустить те же проверки локально

Из корня проекта с активированным venv и установленными dev-зависимостями:

```bash

python -m pip check
python -m compileall -q services shared scripts tests
python -m pytest -q
python -m scripts.verify_accuracy --report accuracy-report.md
node --experimental-default-type=module scripts/check_assistant_ui_logic.mjs
node --experimental-default-type=module scripts/check_analysis_ui_logic.mjs
```

Для проверки именно Docker-поставки дополнительно выполните:

```bash

docker compose build --parallel
docker build --target tests -t well-model-builder-tests:local .
docker run --rm well-model-builder-tests:local
NGINX_PORT=18000 docker compose up -d --build --wait
docker compose exec -T backend python scripts/smoke.py --compose
docker compose down --remove-orphans --volumes
```

На Windows PowerShell последнюю команду запуска с переменной окружения выполните так:

```powershell
$env:NGINX_PORT = "18000"
docker compose up -d --build --wait
```

Браузерный Playwright-прогон `scripts/check_assistant_ui.py` оставлен дополнительной ручной проверкой: ему нужны Playwright и установленный Chromium. Проверка живой LLM также выполняется отдельно на машине, где настроен выбранный провайдер; CI намеренно не обращается к платной/внешней модели.

## Проверка точности

Из корня распакованного проекта выполните в PowerShell с Python 3.12:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m scripts.verify_accuracy
```

Если окружение проекта уже готово, достаточно последней команды. Для Linux или macOS используйте `python3.12` и `.venv/bin/python`. Команда запускает unittest, поднимает отдельные процессы IPR, VLP, Nodal и backend на свободных локальных портах, ждёт health, отправляет реальные HTTP-запросы, записывает [таблицу проверки](accuracy-report.md) и останавливает процессы. Можно оставить дашборд открытым. Код завершения 0 означает, что все запрошенные проверки пройдены. Код 1 и строки FAIL указывают на ошибку.

В текущем архиве `pytest -q` собирает 136 тестов (186 subtests); отдельный unittest-набор, который также запускает `scripts.verify_accuracy`, содержит 63 теста. Контрольный прогон: 136 passed / 186 subtests passed, а `scripts.verify_accuracy` завершился с результатом 129 OK / 0 FAIL. Отчёт охватывает аналитические, HTTP- и E2E-проверки, включая сверку well_01. Те же проверки автоматически запускаются в GitHub Actions при `push` и `pull_request` — подробности см. в разделе «CI: автоматическая проверка GitHub Actions». Для воспроизводимой установки используйте Python 3.12 и закреплённые зависимости из `requirements.lock` / `requirements-dev.lock`. [Сравнение исходной и обновлённой моделей](docs/well_01_comparison.md).

**Откуда взялся численный контроль.** В водяном примере пластовое давление 30 атм, PI = 0,1 м³/(сут·атм), устьевое давление 10 атм. Вертикальная глубина 110 м, длины участков 100 и 50 м, диаметры 0,062 и 0,100 м. При дебитах 0–4 м³/сут течение ламинарное. Независимые формулы в проверке задают IPR как `p = 30 − 10q` и VLP как `p = p₀ + kq`, где `p₀ = 10 + ρg·110/101325`, а `k = 128μ·(100/0,062⁴ + 50/0,100⁴)/(π·86400·101325)`. Здесь ρ = 1000 кг/м³ и μ = 0,001 Па·с. Решение двух уравнений даёт эталон E2E. Для каждого ненулевого значения сравнивается `100 × |факт − эталон| / |эталон|`. Предел включён, 5 % для каждого сервиса и 10 % для обеих координат E2E. Для нулевого эталона принято точное совпадение с нулём, в таблице показано абсолютное отклонение в единицах координаты.

### Эталоны well_01

Команда проверки выше автоматически использует оригинальные запросы и ответы в `test_data/well_01`. Для другого набора можно указать `--references путь/к/manifest.json --report другой-отчёт.md`. Пути внутри карты отсчитываются от её папки. У well_01 запрос Nodal содержит точные копии обеих эталонных кривых. Поэтому для E2E используется та же эталонная рабочая точка. Backend каждый раз получает исходные параметры скважины и рассчитывает обе кривые заново.

| Давления VLP, атм | HTTP | Результат |
| --- | --- | --- |
| `[1,3]` | 200 | Пересечение между узлами при 1 м³/сут и 2 атм |
| `[3,4]` | 200 | Общий конец при 0 м³/сут и 3 атм |

### Как рассчитывается подъём

- Разбиваем ствол по станциям инклинометрии, башмаку НКТ и точке пласта. Линейная интерполяция TVD по MD даёт вертикальный уклон каждого участка. Если первая станция глубже устья, добавляем начало в (0, 0). При `h_mes=0` весь ствол проходит по эксплуатационной колонне.
- Принят постоянный геотермический градиент по вертикали. Местная температура равна `t_res − geo_grad × (TVD(h_res) − TVD(MD)) / 100`. Для скважины из примера это 57 °C на устье, 87 °C у башмака и 90 °C у пласта.
- Давление интегрируется от заданного `p_wh` вниз методом RK45 с отдельным шагом запуска на каждой границе участков. Градиент в Па/м равен `ρg × dTVD/dMD + f × ρv²/(2d)`. При подъёме потока обе составляющие увеличивают требуемое давление на забое. На горизонтальном участке гидростатическая составляющая равна нулю. Скорость определяется по локальному рабочему объёму всех фаз, при нулевом расходе остаётся гидростатика однородной равновесной смеси.
- Для Re ≤ 2000 применяется ламинарная формула, для Re ≥ 4000 итерационно решается уравнение Colebrook–White для коэффициента Дарси. Переход между граничными значениями линейный. `roughness` подаётся сразу как отношение абсолютной шероховатости к диаметру. [Уравнения Дарси–Вейсбаха и Colebrook–White](https://www.aiche.org/sites/default/files/cep/20161238_r.pdf)

## Расчёт IPR

После запуска всего проекта в Docker откройте [Swagger IPR](http://localhost/ipr/docs). Выберите `POST /ipr/calc`, нажмите **Try it out** и **Execute**. В форму уже подставлен пример из §5.2 ТЗ.

| Поле | Смысл и единицы | Допустимые значения |
| --- | --- | --- |
| `p_res` | Пластовое давление, атм | Больше 0 |
| `wct` | Обводнённость жидкости, % | От 0 до 100 включительно |
| `pi` | Коэффициент продуктивности, м³/(сут·атм) | 0 и выше |
| `pb` | Давление насыщения, атм | 0 и выше |
| `points` | Число точек | Целое от 2 до 201, по умолчанию 21 |

Первые четыре поля обязательны. При ошибке ввода сервис возвращает HTTP 422 и JSON с полем `detail`. В ответе на корректный запрос элементы `p_wf[i]` и `q_liq[i]` образуют одну точку. Давления расположены с равным шагом от 1 атм до `p_res`, оба конца включены. При `p_wf = p_res` дебит равен нулю.

**Контрольный запрос для PowerShell**

```powershell
$body = '{"p_res":200,"wct":100,"pi":1,"pb":150,"points":2}'
Invoke-RestMethod -Method Post -Uri 'http://localhost/ipr/calc' -ContentType 'application/json' -Body $body | ConvertTo-Json -Compress
```

```json
{"q_liq":[199.0,0.0],"p_wf":[1.0,200.0]}
```

Для примера из ТЗ задайте `wct=50` и опустите `points`. При 1 и 10,95 атм первые дебиты, округлённые до сотых, равны 139,98 и 137,93 м³/сут. API отдаёт числа с полной точностью расчёта.

### Формула и граничные случаи

Обозначим `J = pi`, `f = wct / 100`, `B = min(pb, p_res)`. Для насыщенного пласта (`pb >= p_res`) форма Вогеля нормируется на пластовое давление. При нулевой продуктивности весь ряд дебитов равен нулю.

1. При 100% воды или при `p_wf >= B` приток равен `J · (p_res − p_wf)` в области добычи. При `pb = 0` это вся кривая.
2. Для чистой нефти ниже `B` положим `q_b = J · (p_res − B)` и `x = p_wf / B`. Тогда `q_oil = q_b + (J · B / 1.8) · (1 − 0.2x − 0.8x²)`. При `p_wf = B` обе ветви дают `q_b`.
3. Для смеси при одном дебите `q` рассчитываются давление воды `p_water = p_res − q/J` и давление нефти `p_oil` по обращённой кривой Вогеля. Brown задаёт `p_wf(q) = f · p_water + (1 − f) · p_oil`. Код решает это уравнение относительно дебита для каждого давления сетки.
4. При `q_o,max = q_b + J · B / 1.8` нефтяное давление достигает нуля, а давление смеси равно `(4/9) · f · B`. Ниже этого давления используется линейное продолжение по секущей композитной кривой через `0.999 · q_o,max` и `q_o,max`.

ТЗ допускает `0 < p_res < 1` и фиксирует начало сетки в 1 атм. Для этого случая сервис сохраняет оба конца убывающей сетки и возвращает нулевой приток во всех точках, где забойное давление достигает или превышает пластовое. При `p_res = 1` все точки имеют давление 1 атм.

Методика — K. E. Brown, *The Technology of Artificial Lift Methods*, т. 4, PennWell, 1984, с. 30–35. Формулы композитной кривой и секущей приведены у A. C. Kahya, *Analyzing the Design of Submersible Lifted Deviated Oil Wells*, METU, 2005, уравнения 3.10–3.26. Расчёт реализован в проекте и выполняется локально. [Библиографическая ссылка на Brown](https://www.ihsenergy.ca/support/documentation_ca/Harmony_Enterprise/2023_2/content/html_files/ref_materials/analysis_method_theory/oil_ipr_theory.htm) · [Уравнения в работе Kahya](https://open.metu.edu.tr/bitstream/handle/11511/14802/index.pdf)

## Контракт дашборда и backend

Дашборд использует `POST /api/calculate` с `Content-Type: application/json`. Дашборд передаёт данные скважины одним запросом. Обводнённость задаётся один раз в `pvt.wct` и используется обеими моделями. Имена входов и выходов расчётных сервисов соответствуют §5 ТЗ.

### Пример запроса

Тот же JSON сохранён в [examples/calculate.json](examples/calculate.json).

```json
{
  "reservoir": {"p_res": 200, "pi": 1, "pb": 150},
  "well": {
    "inclinometry": {"MD": [0, 1000, 1500], "TVD": [0, 1000, 1100]},
    "casing": {"d": 0.1},
    "tubing": {"d": 0.062, "h_mes": 1000},
    "p_wh": 10, "geo_grad": 3, "h_res": 1500, "roughness": 0.0001
  },
  "pvt": {"wct": 100, "rp": 100, "gamma_oil": 0.8, "gamma_gas": 0.7, "gamma_wat": 1.0, "t_res": 90},
  "sampling": {"ipr_points": 2, "vlp_points": 2, "q_max": 200}
}
```

| Блок | Поля и единицы |
| --- | --- |
| `reservoir` | `p_res` и `pb` в атм, `pi` в м³/(сут·атм). `pb` передаётся в IPR. |
| `well` | `MD`, `TVD`, диаметры `d`, `h_mes`, `h_res` в м, `p_wh` в атм. Относительная шероховатость `roughness` по умолчанию равна 0.0001. Для `geo_grad` команда принимает °C/100 м. |
| `pvt` | `wct` в %, `rp` в м³/т, `gamma_oil`, `gamma_gas`, `gamma_wat` — относительные плотности, `t_res` в °C. |
| `sampling` | Весь блок можно опустить. По умолчанию по 21 точке IPR и VLP и `q_max = 400` м³/сут. Каждая сетка допускает от 2 до 201 точки. |

Числа передаются как конечные JSON-числа. Backend проверяет типы, диапазоны и согласованность геометрии. Имена полей MD и TVD чувствительны к регистру.

### Формат успешного ответа

Для запроса из примера backend возвращает HTTP 200. Значения ниже округлены до пяти знаков.

```json
{
  "ipr": {"q_liq": [199, 0], "p_wf": [1, 200]},
  "vlp": {"q_liq": [0, 200], "p_wf": [116.46252, 117.51846]},
  "operating_point": {"q_liq": 83.09874, "p_wf": 116.90126}
}
```

Пара элементов `q_liq[i]` (м³/сут) и `p_wf[i]` (атм) задаёт узел кривой. Backend отправляет Nodal исходные узлы с полной точностью. Единственный элемент ответа Nodal становится объектом `operating_point`.

### Контрольные сценарии

Каждая строка задаёт отдельное изменение исходного файла `examples/calculate.json`.

| Изменение | HTTP | Что проверить |
| --- | --- | --- |
| Установить `pvt.wct = 50` и удалить блок `sampling` | 200 | По 21 точке в обеих кривых. Рабочая точка около 127,99036 м³/сут и 49,70857 атм. |
| Установить `pvt.wct = 101` | 422 | Backend указывает путь `body.pvt.wct`. |
| Установить `well.p_wh = 210` | 422 | `NODAL — Кривые IPR и VLP не пересекаются.` |
| Отправить исходный запрос при недоступном VLP | 503 | `VLP — сервис недоступен.` |

Ошибки возвращаются как JSON с полем `detail`. При превышении времени ожидания backend возвращает HTTP 504, при повреждённом или неожиданном ответе сервиса — HTTP 502. В обоих случаях указан этап.

## Нативный запуск без Docker/Podman (Python + venv)

Этот режим запускает все пять компонентов обычными Python-процессами: IPR, VLP, Nodal, Backend и локальный HTTP-сервер Frontend. Docker, Podman, Compose и системный Nginx не требуются. Режим предназначен для локальной демонстрации, разработки и проверки на машине, где нельзя устанавливать контейнерный runtime.

**Требования**

- CPython 3.12 (рекомендуемая версия; код использует синтаксис Python 3.12). На 64-битных Windows, Linux и macOS зависимости устанавливаются из закреплённого lock-файла через pip.
- Доступ к PyPI на этапе первой установки зависимостей. После установки venv приложение может запускаться без доступа к PyPI.
- Для интерфейса нужен современный браузер. Для самой расчётной части не нужны LLM, Ollama, база данных, Docker или внешние API.
- Node.js нужен только для JavaScript-проверок из раздела «Тесты», не для работы приложения.

Все команды запуска выполняются из корневой папки распакованного проекта — там, где находятся `requirements.lock`, `scripts/` и `services/`.

### Windows 10/11 · PowerShell

.\.venv\Scripts\python.exe -m pip install -r requirements.lock
```

```

После появления сообщения `Все пять компонентов Well Model Builder готовы` откройте:

- Dashboard: `http://127.0.0.1:3000/`
- Страница состояния сервисов: `http://127.0.0.1:3000/services.html`
- Backend Swagger: `http://127.0.0.1:8080/docs`
- IPR Swagger: `http://127.0.0.1:8003/docs`
- VLP Swagger: `http://127.0.0.1:8002/docs`
- Nodal Swagger: `http://127.0.0.1:8004/docs`

Окно PowerShell с `run_local.py` должно оставаться открытым. Нажмите `Ctrl+C`, чтобы остановить все пять процессов.

### Что запускает run_local.py

Скрипт стартует каждый компонент отдельным процессом Uvicorn и ждёт, пока каждый ответит на health-check (Frontend проверяется HTTP-запросом к `/`). Если один из процессов не запустится или завершится, скрипт сообщает, какой компонент не готов, и останавливает остальные процессы.

| Компонент | Адрес при стандартном запуске | Назначение |
| --- | --- | --- |
| Frontend | `127.0.0.1:3000` | Статические файлы Dashboard через `scripts/local_frontend.py` |
| Backend | `127.0.0.1:8080` | Оркестратор, Well AI, сценарии, анализ и API |
| VLP | `127.0.0.1:8002` | Кривая подъёма и PVT |
| IPR | `127.0.0.1:8003` | Кривая притока |
| Nodal | `127.0.0.1:8004` | Поиск рабочей точки |

В нативном режиме Frontend получает фактический порт Backend из `/backend-port.js` и обращается к Backend/IPR/VLP/Nodal напрямую по их локальным портам. Поэтому все пять процессов должны работать одновременно. На странице `services.html` можно проверить их health, а `scripts/smoke.py` проверяет HTTP-контракты и сквозной расчёт.

### Доступ к Dashboard с другой машины в локальной сети

По умолчанию все процессы слушают только `127.0.0.1`, поэтому доступ с других компьютеров закрыт. Для временной демонстрации внутри доверенной LAN можно явно открыть listener на всех интерфейсах:

Linux/macOS:

```bash
export FRONTEND_ORIGINS="http://192.168.1.50:3000"
.venv/bin/python scripts/run_local.py --host 0.0.0.0
```

Windows PowerShell:

```powershell
$env:FRONTEND_ORIGINS = "http://192.168.1.50:3000"
.\.venv\Scripts\python.exe scripts/run_local.py --host 0.0.0.0
```

Замените `192.168.1.50` на IP компьютера, с которого открывается Dashboard. На сервере нужно разрешить входящие TCP-подключения к портам `3000`, `8080`, `8002`, `8003` и `8004` только из вашей локальной сети. Frontend обращается к API напрямую на эти порты, поэтому одного порта 3000 недостаточно. При выбранном `--backend-port` откройте вместо 8080 этот порт и передайте тот же параметр `scripts/smoke.py`.

**Не открывайте этот режим напрямую в Интернет.** Нативный launcher не настраивает TLS, авторизацию или reverse proxy; для публичного размещения используйте Docker Compose с Nginx либо настройте отдельный системный reverse proxy и контроль доступа. После LAN-демонстрации вернитесь к стандартному запуску без `--host 0.0.0.0`.

### Well AI при нативном запуске (необязательно)

Расчётная часть, Dashboard, импорт файлов и отчёты работают без LLM-ключа. Для Well AI нужен отдельно запущенный Ollama или доступный OpenAI-совместимый API. При нативном запуске переменные передаются в окружение процесса; `scripts/run_local.py` **не загружает `.env` автоматически**. Файл `.env` и адреса вида `http://ipr:8003` предназначены для Docker Compose. Не используйте Docker-адрес `host.docker.internal` в нативном режиме, если провайдер модели работает на той же машине.

Пример для локальной Ollama на той же машине:

Linux/macOS:

```bash
export LLM_BASE_URL="http://127.0.0.1:11434/v1"
export LLM_MODEL="qwen3:8b"
export LLM_API_KEY="ollama"
export LLM_TIMEOUT="120"
.venv/bin/python scripts/run_local.py
```

Windows PowerShell:

```powershell
$env:LLM_BASE_URL = "http://127.0.0.1:11434/v1"
$env:LLM_MODEL = "qwen3:8b"
$env:LLM_API_KEY = "ollama"
$env:LLM_TIMEOUT = "120"
.\.venv\Scripts\python.exe scripts/run_local.py
```

Сначала установите и запустите Ollama, затем загрузите модель командой `ollama pull qwen3:8b`. Для удалённого API укажите его OpenAI-совместимый Base URL, точное имя модели и ключ. Не записывайте секреты в README, Git или релизный ZIP.

### Ограничения нативного режима

- Вместо Nginx используется небольшой FastAPI/StaticFiles сервер из `scripts/local_frontend.py`; он отдаёт ту же папку `frontend/`. Все API запускаются отдельными процессами Uvicorn.
- Swagger UI на нативном запуске загружает статические JS/CSS с CDN jsDelivr. При отключённом Интернете сами API и Dashboard продолжают работать, но интерактивный Swagger UI может не загрузить оформление и скрипты. В Docker эти файлы копируются в образ из стадии `swagger_assets`.
- Для постоянного серверного запуска используйте менеджер процессов ОС (например, systemd на Linux/Windows Service) либо контейнерный вариант. Обычный `run_local.py` — foreground launcher: закрытие терминала останавливает приложение.
- Расчёты не зависят от внешних API. LLM — дополнительная функция; отсутствие модели или ключа не блокирует IPR, VLP, Nodal и общий расчёт.

## Well v7 — интерфейс и сценарии (этап 4 ассистента)

### Диалог и сохранение

Сообщения занимают собственную высоту в прокручиваемой области, лишние пустые строки сокращаются, жирный текст Markdown отображается безопасно, а длинный JSON свернут. История последних 100 сообщений (при нехватке места — меньше), идентификатор сессии, последнее состояние формы и результат чата сохраняются в `localStorage` данного браузера и адреса сайта. Кнопка «+» очищает текущую историю и начинает новую сессию. Серверный контекст хранится в памяти backend с TTL 1 час; после перезапуска backend или истечения срока локальная переписка останется, но для расчёта понадобится снова передать форму. Данные не синхронизируются между браузерами и профилями. При выключенном или переполненном хранилище история может не сохраниться. Результаты из обычного чата сохраняются, серия из отдельной панели существует до обновления страницы.

### Сценарии и подбор

1. Заполните исходную форму. Откройте раздел «Сценарии». Выберите один параметр, цель (сравнение, максимум дебита или минимум забойного давления), диапазон и число точек (1–8). Для одного варианта задайте одинаковые границы и число 1.
2. «Выполнить серию» отправляет снимок текущей формы в backend. Базовый режим рассчитывается отдельно, остальные параметры фиксируются. Все кандидаты проверяются общей валидацией. Ошибочный режим или отсутствие пересечения не получают рабочей точки и исключаются из подбора.
3. Таблица показывает исходную точку, варианты, абсолютные изменения относительно базового режима, ошибки и предупреждения. Кнопка «Показать» строит кривые выбранного режима и накладывает базовые кривые, если базовая точка найдена. «Перенести выбранный режим в форму» — явное действие пользователя, после него основной расчёт можно повторить. Автоматически исходная форма не изменяется.
4. Оптимизация — дискретный перебор равномерной сетки заданного диапазона, не непрерывная глобальная оптимизация. Равные целевые результаты: выбирается первый среди проверенных. Дополнительных ограничений по режиму, кроме валидации и заданных границ, не введено. Не используются газлифт, ЭЦН или другие механизмы за пределами ТЗ.

В чате сначала нажмите «Рассчитать по форме» или передайте полный JSON/текст. Затем поддерживаются явные команды:

- `Что если устьевое давление 15 атм?`
- `Сравни обводнённость 70 %`
- `Подбери устьевое давление от 5 до 15 атм, 5 вариантов, максимум дебита`
- `Подбери устьевое давление от 5 до 15 атм, 5 вариантов, минимум забойного давления`

Команды выполняются сервером без дополнительных вызовов LLM; обычные вопросы остаются в диалоговом режиме. В чате базой служат подтверждённые параметры сессии; при ручном изменении формы сначала согласуйте её с чатом. Для иных формулировок используйте панель сценариев или показанный синтаксис. Необходимые числовые результаты формирует backend, а не LLM. Серия ограничена 8 кандидатами и базой, общим таймаутом 175 секунд. Ручная панель не требует настройки LLM.

### API

`POST /api/scenarios/run` принимает `baseline` (полный объект `CalculateRequest`, включая согласованные значения по умолчанию), `parameter` (путь к поддерживаемому скалярному полю), `values` (1–8 различных чисел в канонических единицах), `objective` (`compare`, `max_flow`, `min_pressure`). Пример: возьмите `examples/calculate.json` как baseline, `parameter: "well.p_wh"`, `values: [5,10,15]`, `objective: "max_flow"`. Ответ содержит `baseline`, `rows`, `best_index` (индекс в rows или null), `duration_ms`, `parameter`, `label`, `unit`, `objective`. Каждая строка содержит параметры, значение, расчётные кривые и рабочую точку либо ошибку, предупреждения, этапы, а для кандидатов — delta (разность с базой или null). Основные API IPR/VLP/Nodal и формулы не изменены.

### Проверка

```powershell
python -m pytest -q
node --experimental-default-type=module scripts/check_assistant_ui_logic.mjs
```

Новые тесты `tests/test_scenarios.py`: сохранение базы, выбор оптимального кандидата, ошибки/отсутствие пересечения, ограничения серии, команды чата и сравнение с независимыми вызовами настоящих HTTP-сервисов. JS-проверка моделирует перезагрузку страницы и восстановление идентификатора и сообщений. Браузерный тест `scripts/check_assistant_ui.py` дополнен проверками перезагрузки и сценариев; для запуска требуется Playwright и Chromium. В среде сборки браузерная навигация на localhost была заблокирована политикой (`ERR_BLOCKED_BY_ADMINISTRATOR`), поэтому визуальная проверка и проверка реальной LLM остаются за пользователем.

## Этап 5 — RAG и работа с файлами

### Теория со ссылками

Ассистент ищет релевантные фрагменты в локальном индексе `services/backend/assistant/knowledge_index.json`. Источники: оригинальное ТЗ 3.1 и методичка «База знаний Разработка модели скважины», копии в `frontend/knowledge/`. В индексе 26 курируемых текстовых фрагментов. Поиск лексический (нормализация слов, частотное взвешивание и совпадение заголовков), без внешних API и эмбеддингов. Не индексируются рисунки, формулы-изображения и вся методичка целиком. В части реализованных требований ТЗ приоритетнее методички.

Контекст добавляется только в обычном диалоге, без расчётных инструментов. LLM получает фрагменты и идентификаторы A/B/C. Сервер преобразует разрешённые маркеры в ссылки и удаляет неизвестные идентификаторы. UI отдельно показывает источники, упомянутые моделью, и дополнительные результаты поиска. Выдержки можно раскрыть, PDF открывается на соответствующей странице, DOCX скачивается целиком с указанием раздела и номеров абзацев. Подтверждение ссылки не является гарантией логической достоверности пересказа модели; сравнивайте с выдержкой. Числовые результаты скважины по-прежнему берутся только из расчётных сервисов. Числовые требования ТЗ можно прочитать в выдержках; произвольные числовые утверждения LLM блокируются.

Вопросы для демонстрации: «Что такое давление насыщения?», «Что такое IPR?», «Чем отличается MD от TVD?», «Как работает метод Вогеля?». Приветствие не запускает поиск или расчёт. Чтобы обновить индекс после замены исходников, проверьте выбранные абзацы в `scripts/build_knowledge.py`, затем выполните `python -m scripts.build_knowledge` и пересоберите backend и nginx.

### Импорт параметров из файлов

В панели Well AI выберите до трёх файлов (суммарно до 5 МБ), нажмите «Извлечь параметры». Проверьте нормализованные значения, источники, пропуски, предупреждения и ошибки. Кнопка «Подтвердить новый набор» явно заменяет параметры текущей скважины; если набор полный и валидный, backend автоматически вызывает IPR, VLP и Nodal. Для неполного ввода продолжите диалог или допишите параметры вручную. Значения по умолчанию по-прежнему требуют согласия. Конфликт между файлами блокирует импорт — исправьте документ или введите значения вручную.

Поддерживаемые структуры:
- JSON: контракт `examples/calculate.json` или IPR/VLP из ТЗ, канонические единицы.
- TXT и текстовый PDF: отдельные строки `параметр: значение единица` либо `параметр значение единица`, например `Устьевое давление: 1 МПа`; массивы MD/TVD в квадратных скобках. PDF до 60 страниц; сканы без текстового слоя не распознаются.
- CSV и XLSX: столбцы A:C `parameter, value, unit` (русские названия и имена API допустимы), CSV с запятой, точкой с запятой или табуляцией. XLSX читается по листам; формулы не вычисляются.
- DOCX: отдельные текстовые абзацы и таблицы из двух/трёх столбцов (параметр, значение, единица). Не поддерживается OCR, произвольные сложные таблицы, вложенные таблицы и распознавание формул/рисунков.

Серверный предварительный просмотр: `POST /api/assistant/files/preview` с `{"files":[{"name":"well.json","content":"<base64>"}],"session_id":"<необязательный UUID>"}`. Сервер возвращает `preview_id`, `session_id`, параметры, происхождение, ошибки и валидацию. `POST /api/assistant/files/confirm` принимает оба UUID, применяет только сохранённый на сервере проверенный набор, токен одноразовый. Само чтение файла не запускает сервисы. Предпросмотр и импорт не требуют LLM; дальнейший чат требует настроенную LLM.

**Защита:** сырые загруженные документы не отправляются LLM и не становятся частью системного промпта, разрешены только известные поля и значения с явными единицами, формулы Excel не исполняются, источники расхождений видны до подтверждения, неизвестные инструкции игнорируются. В документах могут быть ложные, но формально валидные исходные числа — их нужно проверить человеком. Ограничения объёма, страниц, строк и распакованных Office-архивов снижают риск, но это не изолированная песочница для потенциально вредоносных PDF/Office. Не выставляйте API публично без отдельной защиты и ограничения запросов. Файлы не сохраняются на диск сервером; параметры и происхождение хранятся в серверной сессии и локальной истории браузера. После перезапуска backend незавершённый предпросмотр надо загрузить заново.

**Проверка:** загрузите по одному `examples/file_import/well.json`, `well.txt`, `well.csv` — результаты должны совпасть с ручным расчётом из `examples/calculate.json`. Затем загрузите `well.json` + `conflict.txt` — подтверждение заблокировано. Загрузите `well.json` + `injection.txt` — искусственный дебит не используется, значения и рабочая точка совпадают с расчётными сервисами. Команды тестов: `python -m pytest -q`, `node --experimental-default-type=module scripts/check_assistant_ui_logic.mjs`. Живую LLM и внешний вид проверяет команда на своём ПК.

## Well v9 — этап 6. Отчёты, замеры и пакетный анализ

Реализованы улучшения № 5, 10 и 12 раздела 6.7 ТЗ. Физические модели, формулы и контракты IPR/VLP/Nodal не менялись. Новые функции работают без LLM; чат дополнительно принимает явные команды.

### Использование

1. `docker compose up -d --build`, открыть `http://localhost/` (либо порт из `NGINX_PORT`). Для LLM перенести собственный `.env` из прежней версии; не включать ключ в архив. После обновления при необходимости обновить страницу Ctrl+F5.
2. Рассчитать скважину обычной кнопкой или через чат. Под графиком доступны HTML-отчёт и Markdown. Отчёт создаётся по снимку входных параметров и ответа backend, не пересчитывает скважину и недоступен при отсутствии актуальной рабочей точки. HTML автономный, содержит график SVG; откройте его и выберите Ctrl+P → «Сохранить как PDF». Markdown содержит тот же график inline SVG и таблицу координат; некоторые Markdown-просмотрщики не отображают SVG, в таком случае используйте HTML. Нативный PDF/DOCX-генератор не добавлялся.
3. Перейти к разделу «Отчёты и пакетный анализ». Указать имя, при наличии — фактический суммарный дебит жидкости и забойное давление в единицах модели; нажать «Добавить текущую форму». Изменить исходные параметры и добавить следующую скважину. Вместо ручного списка можно загрузить `examples/batch.json` (он же доступен по ссылке на странице). Учебные замеры в файле искусственные, а не реальные промысловые данные.
4. Указать порог отклонения в процентах и нажать «Рассчитать пакет». Выводятся рассчитанные точки, замеры, абсолютные (со знаком) и относительные отклонения по обеим координатам, статус, диагностика и график выбранной строки. Некорректные входные параметры или отсутствие рабочей точки не останавливают остальные корректные скважины. Пакет с нарушенным внешним JSON-контрактом отклоняется целиком. Изменение списка сбрасывает предыдущий результат пакета. Можно сохранить сводный CSV (UTF-8 BOM, разделитель `;`), HTML или MD; HTML/MD содержат данные, допущения, результаты, диагностические замечания и графики всех успешных режимов.
5. Для подбора PI ввести фактический дебит в верхней части панели, указать диапазон PI и число вариантов, нажать «Подобрать PI». Базовая скважина — текущая форма; лучший вариант минимизирует абсолютную разницу между расчётным и фактическим дебитом на дискретной сетке. Неудачные варианты исключаются. Режим переносится в форму только по отдельной кнопке. Это подбор одного параметра по одному замеру, не доказательство физической достоверности PI и не непрерывная оптимизация.
6. После «Рассчитать по форме» в чате: `Сформируй отчёт`, `Сравни с фактическим дебитом 100 м³/сут`, `Подбери PI по фактическому дебиту 100 м³/сут от 0.5 до 2, 5 вариантов`. Команды распознаются сервером по указанным формулировкам; не требуют генерации чисел LLM. Для произвольных формулировок используйте панель. Чат использует только свой последний успешный расчёт; при изменённой вручную форме сначала передайте её в чат. Пакетная обработка запускается в панели, не через свободный текст LLM.

### Контракты

- `POST /api/analysis/batch`: `{"wells":[{"name":"A","parameters":{...полный CalculateRequest...},"measured":{"q_liq":75,"p_wf":125}}],"deviation_threshold":10}`. `measured` может отсутствовать, давление необязательно; если указан замер, требуется дебит. До 8 скважин с уникальными именами. Поля с расчётными значениями по умолчанию указываются явно. Ответ: `rows`, `total`, `successful`, `flagged`, `deviation_threshold`; каждая строка содержит исходные данные, расчёт или ошибку, сравнение, предупреждения и этапы.
- `POST /api/analysis/calibrate`: `{"well":{...одна скважина...},"pi_min":0.5,"pi_max":2,"count":5}`. До 8 значений PI, границы включены, 2–8 вариантов; нужен замер дебита. Ответ: `baseline`, `rows`, `best_index` (индекс среди вариантов, не включая базу; `null`, если ни один не рассчитан).
- Отклонение = расчёт − факт, относительное отклонение = отклонение / факт × 100 %. При нулевом факте процент не определён (`null`), ненулевое абсолютное отклонение отмечается. Превышение порога по любому предоставленному замеру отмечает строку. Для подбора PI и чат-сравнения диагностический порог фиксирован 10 %, для пакетной панели настраивается. Гипотезы о причинах — не установленные диагнозы. Сравниваются только замеры, полученные при сопоставимых условиях.
- Пакет и калибровка выполняются последовательно с общим ограничением времени ~170 с и ограничением на отдельный вызов; незавершённая строка возвращает ошибку. Числа рабочих точек берутся только из `calculate`, разницы вычисляет Python. Пакетные результаты хранятся в текущей странице (не в БД); их следует выгрузить до перезагрузки. История чата сохраняется как в v8, включая последние результаты сравнения/отчёта.
