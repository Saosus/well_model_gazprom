# Well Model Builder

Версия с формулами базы знаний, на основе этапа 08 хакатона «Разработка системы модели скважины». Дашборд строит IPR и VLP и показывает рабочую точку. Автотесты проверяют расчётные сервисы по отдельности и весь путь от параметров скважины до ответа backend.

## Проверка точности

Из корня распакованного проекта выполните в PowerShell с Python 3.12:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m scripts.verify_accuracy
```

Если окружение проекта уже готово, достаточно последней команды. Для Linux или macOS используйте `python3.12` и `.venv/bin/python`. Команда запускает unittest, поднимает отдельные процессы IPR, VLP, Nodal и backend на свободных локальных портах, ждёт health, отправляет реальные HTTP-запросы, записывает [таблицу проверки](accuracy-report.md) и останавливает процессы. Можно оставить дашборд открытым. Код завершения 0 означает, что все запрошенные проверки пройдены. Код 1 и строки FAIL указывают на ошибку.

На Python 3.12.14 прошли 58 автотестов. Отчёт содержит 129 успешных строк с учётом аналитических и HTTP-проверок. В том числе по архиву well_01 сверены 88 чисел. [Сравнение исходной и обновлённой моделей](docs/well_01_comparison.md).

**Откуда взялся численный контроль.** В водяном примере пластовое давление 30 атм, PI = 0,1 м³/(сут·атм), устьевое давление 10 атм. Вертикальная глубина 110 м, длины участков 100 и 50 м, диаметры 0,062 и 0,100 м. При дебитах 0–4 м³/сут течение ламинарное. Независимые формулы в проверке задают IPR как `p = 30 − 10q` и VLP как `p = p₀ + kq`, где `p₀ = 10 + ρg·110/101325`, а `k = 128μ·(100/0,062⁴ + 50/0,100⁴)/(π·86400·101325)`. Здесь ρ = 1000 кг/м³ и μ = 0,001 Па·с. Решение двух уравнений даёт эталон E2E. Для каждого ненулевого значения сравнивается `100 × |факт − эталон| / |эталон|`. Предел включён, 5 % для каждого сервиса и 10 % для обеих координат E2E. Для нулевого эталона принято точное совпадение с нулём, в таблице показано абсолютное отклонение в единицах координаты.

### Эталоны well_01

Команда проверки выше автоматически использует оригинальные запросы и ответы в `test_data/well_01`. Для другого набора можно указать `--references путь/к/manifest.json --report другой-отчёт.md`. Пути внутри карты отсчитываются от её папки. У well_01 запрос Nodal содержит точные копии обеих эталонных кривых. Поэтому для E2E используется та же эталонная рабочая точка. Backend каждый раз получает исходные параметры скважины и рассчитывает обе кривые заново.

| Давления VLP, атм | HTTP | Результат |
| --- | --- | --- |
| `[1,3]` | 200 | Пересечение между узлами при 1 м³/сут и 2 атм |
| `[3,4]` | 200 | Общий конец при 0 м³/сут и 3 атм |

### Как рассчитывается подъём

- Разбиваем ствол по станциям инклинометрии, башмаку НКТ и точке пласта. Линейная интерполяция TVD по MD даёт вертикальный уклон каждого участка. Если первая станция глубже устья, добавляем начало в (0, 0). При `h_mes=0` весь ствол проходит по эксплуатационной колонне.
- Принят постоянный геотермический градиент по вертикали. Местная температура равна `t_res − geo_grad × (TVD(h_res) − TVD(MD)) / 100`. Для скважины из примера это 57 °C на устье, 87 °C у башмака и 90 °C у пласта.
- Давление интегрируется от заданного `p_wh` вниз методом RK45 с отдельным шагом запуска на каждой границе участков. Градиент в Па/м равен `ρg × dTVD/dMD + f × ρv²/(2d)`. При подъёме потока обе составляющие увеличивают требуемое давление на забое. На горизонтальном участке гидростатическая составляющая равна нулю. Скорость определяется по локальному рабочему объёму всех фаз, при нулевом расходе остаётся гидростатика однородной равновесной смеси.
- Для Re ≤ 2000 применяется ламинарная формула, для Re ≥ 4000 итерационно решается уравнение Colebrook–White для коэффициента Дарси. Переход между граничными значениями линейный. `roughness` подаётся сразу как отношение абсолютной шероховатости к диаметру. [Уравнения Дарси–Вейсбаха и Colebrook–White](https://www.aiche.org/sites/default/files/cep/20161238_r.pdf)

## Запуск в Docker

Требуются Docker Engine и Docker Compose v2. Все контейнеры приложения работают в отдельной внутренней Docker-сети `app_internal`. Порты IPR, VLP, Nodal и Backend **не публикуются на хост**. Единственная точка входа — контейнер Nginx: он раздаёт статический frontend из собственного образа и проксирует запросы к backend и трём расчётным API.

### Полный запуск без публикации портов

Из каталога, где находится `compose.yaml`, выполните:

```bash
docker compose --profile app up -d --build
docker compose --profile app ps
docker compose --profile app exec -T backend python scripts/smoke.py --compose --proxy http://nginx
```

Этот режим предназначен для подключения внешнего reverse proxy по общей Docker-сети. Самостоятельно с хоста приложение недоступно — это намеренное поведение, а не ошибка запуска.

### Локальный доступ через один порт Nginx

Для проверки на рабочей станции подключите дополнительный Compose-файл. Он публикует только Nginx на loopback; внутренние порты сервисов остаются закрытыми от хоста.

```bash
docker compose -f compose.yaml -f compose.local.yaml --profile app up -d --build
docker compose -f compose.yaml -f compose.local.yaml --profile app exec -T backend python scripts/smoke.py --compose --proxy http://nginx
```

Откройте `http://127.0.0.1:8080/`. Порт можно изменить через `HTTP_PORT` в `.env`; адрес привязки по умолчанию — `127.0.0.1`. Не меняйте его на `0.0.0.0`, если перед приложением не настроены TLS и ограничения доступа.

### Подключение к существующему Nginx через Docker-сеть

На сервере один раз создайте внешнюю сеть (или укажите уже существующую через `PROXY_NETWORK`):

```bash
docker network create public_proxy
```

Запустите WMB с дополнительным Compose-файлом:

```bash
docker compose -f compose.yaml -f compose.proxy.yaml --profile app up -d --build
```

Внешний Nginx должен быть подключён к той же сети `public_proxy`. Для контейнера WMB в ней зарегистрирован DNS-алиас `well-model-builder`. Если внешний Nginx находится в отдельном Compose-проекте, в его `compose.yaml` подключите только сам reverse proxy к этой сети:

```yaml
services:
  nginx:
    networks:
      - default
      - public_proxy

networks:
  public_proxy:
    external: true
    name: public_proxy
```

В конфигурации внешнего Nginx используйте отдельный домен (приложение рассчитано на размещение в корне virtual host, а не в подпапке):

```nginx
server {
    # На обычном сервере используйте 443. Если порт занят Xray,
    # можно использовать 8444 и открыть его в firewall.
    listen 8444 ssl;
    server_name wmb.example.org;

    ssl_certificate /etc/letsencrypt/live/wmb.example.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/wmb.example.org/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://well-model-builder:80;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 70s;
        proxy_send_timeout 70s;
    }
}
```

Если внешний Nginx работает на том же VPS, его Compose должен опубликовать выбранный внешний порт контейнера 443 (например, `8444:443`). Порт 443 хоста можно оставить Xray. Сертификат и ACME HTTP-01 обслуживаются существующим Certbot; challenge на порту 80 должен продолжать работать.

Ограничения доступа, Basic Auth и rate limiting при публичной публикации рекомендуется задавать на внешнем edge Nginx. Контейнерный Nginx WMB отвечает за маршрутизацию внутри приложения и не публикует порт на хост в этом режиме.

### Остановка

```bash
docker compose --profile app down
```

Данные приложения не хранятся в bind mounts или named volumes; пересоздание контейнеров не требует сохранения изменяемых данных. Если позднее появятся пользовательские загрузки или БД, для них нужно добавить отдельные постоянные тома.

| --- | --- | --- |
| `p_res` | Пластовое давление, атм | Больше 0 |
| `wct` | Обводнённость жидкости, % | От 0 до 100 включительно |
| `pi` | Коэффициент продуктивности, м³/(сут·атм) | 0 и выше |
| `pb` | Давление насыщения, атм | 0 и выше |
| `points` | Число точек | Целое от 2 до 201, по умолчанию 21 |

Первые четыре поля обязательны. При ошибке ввода сервис возвращает HTTP 422 и JSON с полем `detail`. В ответе на корректный запрос элементы `p_wf[i]` и `q_liq[i]` образуют одну точку. Давления расположены с равным шагом от 1 атм до `p_res`, оба конца включены. При `p_wf = p_res` дебит равен нулю.

**Контрольный запрос для PowerShell**

```powershell
$body = '{"p_res":200,"wct":100,"pi":1,"pb":150,"points":2}'
Invoke-RestMethod -Method Post -Uri 'http://localhost:8003/ipr/calc' -ContentType 'application/json' -Body $body | ConvertTo-Json -Compress
```

```json
{"q_liq":[199.0,0.0],"p_wf":[1.0,200.0]}
```

Для примера из ТЗ задайте `wct=50` и опустите `points`. При 1 и 10,95 атм первые дебиты, округлённые до сотых, равны 139,98 и 137,93 м³/сут. API отдаёт числа с полной точностью расчёта.

### Формула и граничные случаи

Обозначим `J = pi`, `f = wct / 100`, `B = min(pb, p_res)`. Для насыщенного пласта (`pb >= p_res`) форма Вогеля нормируется на пластовое давление. При нулевой продуктивности весь ряд дебитов равен нулю.

1. При 100% воды или при `p_wf >= B` приток равен `J · (p_res − p_wf)` в области добычи. При `pb = 0` это вся кривая.
2. Для чистой нефти ниже `B` положим `q_b = J · (p_res − B)` и `x = p_wf / B`. Тогда `q_oil = q_b + (J · B / 1.8) · (1 − 0.2x − 0.8x²)`. При `p_wf = B` обе ветви дают `q_b`.
3. Для смеси при одном дебите `q` рассчитываются давление воды `p_water = p_res − q/J` и давление нефти `p_oil` по обращённой кривой Вогеля. Brown задаёт `p_wf(q) = f · p_water + (1 − f) · p_oil`. Код решает это уравнение относительно дебита для каждого давления сетки.
4. При `q_o,max = q_b + J · B / 1.8` нефтяное давление достигает нуля, а давление смеси равно `(4/9) · f · B`. Ниже этого давления используется линейное продолжение по секущей композитной кривой через `0.999 · q_o,max` и `q_o,max`.

ТЗ допускает `0 < p_res < 1` и фиксирует начало сетки в 1 атм. Для этого случая сервис сохраняет оба конца убывающей сетки и возвращает нулевой приток во всех точках, где забойное давление достигает или превышает пластовое. При `p_res = 1` все точки имеют давление 1 атм.

Методика — K. E. Brown, *The Technology of Artificial Lift Methods*, т. 4, PennWell, 1984, с. 30–35. Формулы композитной кривой и секущей приведены у A. C. Kahya, *Analyzing the Design of Submersible Lifted Deviated Oil Wells*, METU, 2005, уравнения 3.10–3.26. Расчёт реализован в проекте и выполняется локально. [Библиографическая ссылка на Brown](https://www.ihsenergy.ca/support/documentation_ca/Harmony_Enterprise/2023_2/content/html_files/ref_materials/analysis_method_theory/oil_ipr_theory.htm) · [Уравнения в работе Kahya](https://open.metu.edu.tr/bitstream/handle/11511/14802/index.pdf)

## Контракт дашборда и backend

Команда использует `POST http://localhost:8080/api/calculate` с `Content-Type: application/json`. Дашборд передаёт данные скважины одним запросом. Обводнённость задаётся один раз в `pvt.wct` и используется обеими моделями. Имена входов и выходов расчётных сервисов соответствуют §5 ТЗ.

### Пример запроса

Тот же JSON сохранён в [examples/calculate.json](examples/calculate.json).

```json
{
  "reservoir": {"p_res": 200, "pi": 1, "pb": 150},
  "well": {
    "inclinometry": {"MD": [0, 1000, 1500], "TVD": [0, 1000, 1100]},
    "casing": {"d": 0.1},
    "tubing": {"d": 0.062, "h_mes": 1000},
    "p_wh": 10, "geo_grad": 3, "h_res": 1500, "roughness": 0.0001
  },
  "pvt": {"wct": 100, "rp": 100, "gamma_oil": 0.8, "gamma_gas": 0.7, "gamma_wat": 1.0, "t_res": 90},
  "sampling": {"ipr_points": 2, "vlp_points": 2, "q_max": 200}
}
```

| Блок | Поля и единицы |
| --- | --- |
| `reservoir` | `p_res` и `pb` в атм, `pi` в м³/(сут·атм). `pb` передаётся в IPR. |
| `well` | `MD`, `TVD`, диаметры `d`, `h_mes`, `h_res` в м, `p_wh` в атм. Относительная шероховатость `roughness` по умолчанию равна 0.0001. Для `geo_grad` команда принимает °C/100 м. |
| `pvt` | `wct` в %, `rp` в м³/т, `gamma_oil`, `gamma_gas`, `gamma_wat` — относительные плотности, `t_res` в °C. |
| `sampling` | Весь блок можно опустить. По умолчанию по 21 точке IPR и VLP и `q_max = 400` м³/сут. Каждая сетка допускает от 2 до 201 точки. |

Числа передаются как конечные JSON-числа. Backend проверяет типы, диапазоны и согласованность геометрии. Имена полей MD и TVD чувствительны к регистру.

### Формат успешного ответа

Для запроса из примера backend возвращает HTTP 200. Значения ниже округлены до пяти знаков.

```json
{
  "ipr": {"q_liq": [199, 0], "p_wf": [1, 200]},
  "vlp": {"q_liq": [0, 200], "p_wf": [116.46252, 117.51846]},
  "operating_point": {"q_liq": 83.09874, "p_wf": 116.90126}
}
```

Пара элементов `q_liq[i]` (м³/сут) и `p_wf[i]` (атм) задаёт узел кривой. Backend отправляет Nodal исходные узлы с полной точностью. Единственный элемент ответа Nodal становится объектом `operating_point`.

### Контрольные сценарии

Каждая строка задаёт отдельное изменение исходного файла `examples/calculate.json`.

| Изменение | HTTP | Что проверить |
| --- | --- | --- |
| Установить `pvt.wct = 50` и удалить блок `sampling` | 200 | По 21 точке в обеих кривых. Рабочая точка около 127,99036 м³/сут и 49,70857 атм. |
| Установить `pvt.wct = 101` | 422 | Backend указывает путь `body.pvt.wct`. |
| Установить `well.p_wh = 210` | 422 | `NODAL — Кривые IPR и VLP не пересекаются.` |
| Отправить исходный запрос при недоступном VLP | 503 | `VLP — сервис недоступен.` |

Ошибки возвращаются как JSON с полем `detail`. При превышении времени ожидания backend возвращает HTTP 504, при повреждённом или неожиданном ответе сервиса — HTTP 502. В обоих случаях указан этап.

## Запуск без Docker (Python + venv)

Этот способ предназначен для демонстрации на компьютерах, где нет Docker или Podman. Контейнеры и системный Nginx не нужны: `scripts/run_local.py` запускает каждый компонент отдельным процессом Python, а `scripts.local_frontend` раздаёт статические файлы интерфейса через Uvicorn.

Нужны:

- Python **3.12** (та же основная версия, что используется в Docker-образе);
- стандартный модуль `venv` и `pip`;
- браузер с включённым JavaScript;
- доступ к PyPI на этапе установки зависимостей. После установки расчёты и frontend работают локально. Для Swagger UI в нативном режиме браузеру также нужен доступ к CDN `cdn.jsdelivr.net`, откуда загружаются его JS и CSS.

Все пять процессов по умолчанию слушают только `127.0.0.1`, поэтому приложение доступно в браузере на том же компьютере и не публикуется в локальную сеть или Интернет.

### Windows 10/11 · PowerShell

Откройте PowerShell в корне распакованного проекта. Проверьте, что установлен Python 3.12:

```powershell
py -3.12 --version
```

Создайте виртуальное окружение и установите runtime-зависимости из lock-файла:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
```

Запустите все компоненты:

```powershell
.\.venv\Scripts\python.exe scripts/run_local.py
```

Активация окружения необязательна: команды выше явно используют Python из `.venv` и не зависят от PowerShell Execution Policy. При желании можно активировать окружение командой `.\.venv\Scripts\Activate.ps1`, после чего вместо полного пути использовать `python`.

### Linux · macOS (Bash/Zsh)

В терминале перейдите в корень распакованного проекта. Убедитесь, что команда `python3.12` указывает именно на Python 3.12:

```bash
python3.12 --version
```

Создайте и активируйте окружение, установите закреплённые зависимости и запустите приложение:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
python scripts/run_local.py
```

На Debian/Ubuntu, если команда `venv` отсутствует, установите пакет `python3.12-venv` для используемой версии Python 3.12 и повторите создание окружения. Не устанавливайте зависимости через системный `pip`: используйте активированное `.venv`.


`requirements-dev.lock` включает runtime-зависимости из `requirements.lock`, поэтому его можно использовать и как единственную команду установки для разработки. `scripts.verify_accuracy` самостоятельно поднимает временные HTTP-процессы, запускает автотесты и обновляет [accuracy-report.md](accuracy-report.md); предварительно запускать `scripts/run_local.py` для этой команды не требуется.

### Дополнительные режимы запуска

**Только расчётные сервисы без Backend и frontend:**

```bash
python scripts/run_local.py --core
python scripts/smoke.py --core
```

**Если порт Backend 8080 занят:** запустите его, например, на 18080. Frontend автоматически получит этот порт через `/backend-port.js`:

```bash
python scripts/run_local.py --backend-port 18080
```

Во втором терминале проверяйте с тем же параметром:

```bash
python scripts/smoke.py --backend-port 18080
```

В этом режиме Swagger Backend будет доступен на `http://127.0.0.1:18080/docs`; остальные порты не меняются. Порт frontend остаётся 3000.

### Остановка и устранение проблем

Чтобы остановить все дочерние процессы, вернитесь в первое окно терминала и нажмите `Ctrl+C`. Закрывать процессы по одному не требуется. Для повторного запуска снова выполните команду `scripts/run_local.py`.

Если при старте появляется `Address already in use` или `WinError 10013`, один из портов уже занят. По умолчанию нативный запуск использует:

| Компонент | Порт | URL |
| --- | ---: | --- |
| Frontend | 3000 | `http://127.0.0.1:3000/` |
| Backend | 8080 | `http://127.0.0.1:8080/` |
| VLP | 8002 | `http://127.0.0.1:8002/` |
| IPR | 8003 | `http://127.0.0.1:8003/` |
| Nodal | 8004 | `http://127.0.0.1:8004/` |

На Linux/macOS занятые порты можно посмотреть командой `ss -ltnp`; на Windows — `Get-NetTCPConnection -LocalPort 3000,8002,8003,8004,8080 -ErrorAction SilentlyContinue`. Если занят только Backend, используйте `--backend-port 18080`. Если занят другой порт, освободите его перед запуском.

По умолчанию сервисы привязаны к loopback (`127.0.0.1`). Не меняйте bind-адреса на `0.0.0.0` для демонстрации в Интернете: нативный режим не включает TLS, аутентификацию и внешний reverse proxy. Для публичного или сетевого развёртывания используйте Docker Compose за внешним Nginx либо отдельно настройте защищённый reverse proxy.

## Структура для продолжения разработки

| Путь | Назначение |
| --- | --- |
| `services/ipr/main.py`, `services/ipr/model.py` | HTTP-маршрут IPR и численная реализация Composite IPR. |

| `services/backend/main.py` | Состояние сервисов, единый расчёт и обработка ошибок расчётных сервисов. |
| `shared/contracts.py`, `shared/api.py` | Схемы JSON и правила HTTP. |
| `frontend/` | Форма параметров, график IPR/VLP, рабочая точка и страница состояния сервисов. |
| `tests/`, `scripts/`, `examples/` | Проверки контрактов, запуск процессов, проверка портов и пример запроса. |
| `requirements.lock`, `requirements-dev.lock` | Закреплённые версии Python-зависимостей приложения и тестов. |
